## User's observed defect

The new R05 input/output-candidate Home bars respond to guitar and metronome. With metronome alone playing, the **right/output-candidate bar fails to react to some audible clicks**. The user asked whether the root cause is the DSP measurement/report rate or the M4 LCD repaint rate, and how audio equipment ordinarily handles transient meter signals. The accompanying earlier request for disjoint, colored, hardware-LED-style bars remains open.

## Live on-device read-only evidence

On the Mac mini connected to the HX Stomp, `tools/io_level_r04_native_ledger.py` read the existing **640-byte M4 event ledger via editor command 0x13**; `tools/metro_led_r03c_probe.py` read the existing **R03C TAP count via command 0x50**. A later one-session audit gathered both commands sequentially at about **36 complete pairs of readings/s**, compared R05's output-source native `0x0002002a / 1` (plus companion `/2`) against the independently advancing TAP LED count, and observed R05's packed 132px Home right bar width. The live preset check returned path 0, slot 7, model 181 **on**. The R03C metronome-active flag also read true. The host sent only read-only editor requests; it did not change bypass, BPM, settings, buffers, presets or firmware.

The hardware native event series and M4 packed right-bar values had **exactly the same high/low classification in each of the 89 complete beat intervals**. In run A, even the intervals with no high peak had 2–5 newly processed source records per ~0.54s beat, but these held quiet levels (typically −50 to −70). Thus this is a **missing peak-amplitude observation in the selected native event record**, not necessarily a missing whole SPI packet. In run B, all 5 misses were early, followed by **28 consecutive peaks successfully registered**. Run C registered every beat. The source event count cadence was correspondingly variable: roughly 5.65, 8.63, then 9.97 per second. The native nonempty M4 message receive cadence was much higher (~46–53/s).

To eliminate TAP accounting / USB request order as an explanation, we separately reclassified peaks in bounded windows around each observed LED-on event, including a generous **−0.10 to +0.20 seconds** offset. The classification remained the same in all three runs. A 65-sample (1.99s) validation of the repository's reproducible read-only auditor independently recorded 3/3 complete intervals visible in both native record and packed bar, with a ~10.06Hz event stream.

**The physical LCD paint-completion count is not exposed by R05 command 0x13.** The `bar_state_changes` field is a packed *intended display state update count*, not the number of actual Home paint executions or successful LCD refreshes. Thus we have strong evidence for upstream missed peaks *in at least the 11 intervals where the M4 bar also remained low*; we cannot yet exclude a **separate secondary repaint problem** when the M4's state does become high. The `0x50` TAP count measures LED transport, not acoustic emission, and the user reports hearing those clicks; we have no mic/analog-capture to independently confirm sound on every TAP.

### The companion second parameter cannot repair the omission

During run C, both `0x0002002a /1` and `/2` published **193 events** each, both gave identical levels for all 700 host snapshots, and both showed peaks on **35/35** beat intervals. Selecting or max-combining `/2` with `/1` did not recover any additional beat. The separate guitar-only R04 experiment had already shown `/2` can be a stale record while `/1` is active; it is not a robust independent rescue source.

### Why *"just make UI faster"* is an incomplete repair

R05 already coalesces repaint requests every **100 RX callbacks**, about 23Hz at the measured 2.3k RX frames/s. It updates M4 packed bar widths immediately when a qualifying native event arrives. The existing source cadence sometimes yields a strong peak on every beat, but intermittently emits no high peak even though the TAP advances. Accelerating repaint to 60fps cannot display an amplitude the M4 never received. A long display hold can make missing peaks less obvious by retaining an old peak, but this **does not restore their true amplitude or prove they occurred**. A TAP-triggered artificial high meter would visually fake a measurement; do not use it as a physical level meter.

## Important SHARC detail: don't prematurely blame simple sampling

Offline disassembly of the exact frozen R03C SHARC image shows that the stock primitive `0x2390` at `PM 0x8da6a` traverses **16 audio samples per processing call**, calculates the largest absolute sample, updates accumulated maxima in `PM(0,I8)` and `PM(1,I8)`, counts windows in `PM(2,I8)`, and queues a level event via stock `0x8cbb8` when the count reaches `DM(0,I0)`. That primitive already has audio-block-level peak aggregation. The currently selected native object/parameter ID `0x0002002a /1` has **not been conclusively mapped to that exact primitive instance, its signal-tap position, its aggregation interval, or the route from SHARC event queue to M4.** Investigate that chain before deciding whether to add or modify any SHARC code. An intermittent bad native report could arise from tap placement, event registration/routing, event transport/publication, consumer timing, or the audio source itself; the three captures isolate the last native-to-M4 symptom but do not pick among these mechanisms.

## What established audio equipment does instead

1. **Measure peaks before the slow display interface.** At DSP/audio-thread rate, keep the **maximum absolute sample (or equivalent PPM integrated peak) over an interval**, rather than simply sampling the latest value on each UI refresh. The existing HXtra compressor GR meter implements this exact architecture: its SHARC wrapper processes every block (16 samples per callback), retains maxima for **64 blocks ≈21ms**, and passes them into the outgoing DSP/M4 frame tail. The M4 handles display conversion/ballistics without requiring DSP work at LCD refresh frequency. See `docs/research/features/gr-meter.md`, `src/sharc/frame_probe.asm`, `src/m4/gr_meter.s`.
2. **Separate measured peaks from UI refresh.** JUCE's official visualiser preserves peak-of-sample-blocks and exposes a separate `setRepaintRate`. Its audio-DSP community describes 30Hz GUI peak metering by transferring each window's **maximum** rather than the instantaneous sample at redraw. [JUCE](https://docs.juce.com/develop/classjuce_1_1AudioVisualiserComponent.html), [discussion](https://forum.juce.com/t/is-polling-a-lot-of-parameters-from-the-audiothread-a-good-strategy/44332/8).
3. **Add meter ballistics after measurement**: near-instantaneous rise on a new true peak, separate controlled fall, optional peak-hold indicator. [Sound Devices 888](https://support.sounddevices.com/hc/en-us/articles/45140568880923-888-User-Guide) documents PPM instantaneous attack, adjustable **400–1600ms release**, and independent **1–5s or infinite peak hold**. [Calrec Audio Primer](https://calrec.com/wp-content/uploads/2018/01/Calrec-Audio-Primer-926-134-Iss-5.pdf) explains fast-attack/slow-release PPM ballistics and optional peak-hold dot for transient visibility. [Sound Devices classic hardware](https://www.sounddevices.com/audio-level-metering-with-sound-devices-field-mixers/) gives an LED peak meter example with 0.1ms attack and 100ms decay. These are design references, **not requirements for this uncalibrated native signal**.
4. **Preserve truthful amplitude measurement.** A visual beat flash driven by TAP is a metronome indicator, distinct from an audio level meter. It may deliberately be added as a separate cue, but must not substitute for a missed acoustic measurement.

## Proposed safe R06 engineering sequence

**First: establish source fidelity.** In an opt-in RAM-only instrumented experiment, add counters for (a) the chosen native record's incoming high peaks, (b) M4 packed-bar peak latches, (c) UI repaint requests, and (d) actual Home paint invocations and delivered high widths. This discriminates a secondary LCD problem. Trace `0x0002002a/1` to its actual SHARC tap/producer and event queue. Determine the stock producer's peak-window length and any conditional event suppression. If a stock peak aggregator can be read/published reliably, preferentially reuse it; avoid new SHARC/audio-path wrappers where possible.

**Second: if independent audio-rate peak publication is truly necessary**, use a narrowly scoped read-only SHARC signal tap at the **verified** input/output bus locations. Aggregate positive absolute maxima per short window (the existing GR meter's ~21ms, 64 blocks is an experimentally supported starting point). Deliver each completed window's maximum to M4 over **existing unused DSP→M4 SPI frame-tail slots** or a checked equivalent, with generation/count discipline so the M4 doesn't silently miss one. Confirm no collision with GR's occupied words 200,216–218,250–251 or the R03C M4→DSP metronome LED event slots 240–241 on the **opposite** transport direction. Do not assume those empty slots remain free without an exact firmware audit.

**Third: UI rendering and peak visibility.** Segmented independent green/amber/red LED bars analogous to HXtra compressor meters; M4-level peak latch across redraw intervals, fast attack, tunable fall and optional single-block peak marker. For ~0.54s-spaced metronome clicks, too-slow PPM decay can leave the bar continuously high, concealing individual events. Initially compare **fast 100–250ms peak visibility** and a **300–500ms fall** to find a readable metronome/guitar balance, while treating separate PPM standards as options. Use the exact native level scale with conservative yellow/red thresholds until external dBFS calibration is complete. Do not synthesize amplitude from TAP.

**Performance and regression controls are non-negotiable.** The earlier HXtra GR revision triggered device freezes in near-DSP-capacity presets (see `docs/research/features/gr-meter.md`). Any SHARC change must be tightly bounded and instruction-budgeted, with stress tests for max-DSP preset, cold boot, GR, NAM, USB Monitor, user DSP Usage %, R03C metronome sync, no preset/global modifications, and a full comparison to the exact installed R03C. No automatic boot, no updater flash, no permanent release before on-device evidence. Source mapping to physical jack/output remains provisional.
