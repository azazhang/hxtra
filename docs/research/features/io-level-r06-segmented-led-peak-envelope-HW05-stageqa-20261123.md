# R06 HW05: segmented green/amber/red native I/O peak meters and direct Home-paint telemetry

Date: 2026-11-23 America/New_York. Status: *offline-built and Mac mini Chrome RAM staged with HTTP 200 verified; physical R06 startup not yet confirmed*. Source branch `experiment/io-level-r06-segmented-led-true-peak-latch-paint-telemetry-20261123`.

## User's two goals and experimentally verified cause

The user requested genuine live-looking hardware LED level meters, modeled on HXtra's disjoint colored compressor GR LEDs, and reported that right output-candidate R05 bar skips some audible metronome clicks. The latter defect was diagnosed on physical R05 in read-only HW04: paired editor commands `0x13` for native SHARC-to-M4 event records and `0x50` for the independent TAP LED event counter showed **9/15, 34/39, 35/35** full metronome beats each with strong native `0x0002002a/1` peaks. In all three runs the M4 *packed raw bar* high counts matched strong native peaks exactly. The 9/15 run had native output-key data only **5.65Hz**, the 35/35 run about **9.97Hz**. The second output native key `/2` exactly duplicated `/1` in the 35/35 run. The stock SHARC `0x2390` primitive was disassembled and already accumulates audio-block-level peaks, so the exact cause of occasional missing high values within the selected `0x0002002a/1` native report remains unproven. This R06 experiment does **not** assume the source is a physical calibrated Main output and **does not fabricate pulses from the metronome beat**. See `docs/research/features/io-level-r05-HW04-transient-visibility-and-professional-peak-meter-methods-20261123.md`.

## R06 changes (M4 only, existing R05 native key mapping preserved)

- **16 distinct LED lights per bar**. Each lit light is **7×5 pixels**, with a 1px dark gap; 16*7+15*1 = 127px plus 2px left margin fits inside the original 132×5 pixel Home gap x24..155 and x164..295 at y113..117. There are **10 green**, **3 amber**, **2 orange**, **1 red** lights at fixed positions. No GR/DSP Usage/widget position change, and the existing background is erased inside only those two Home stripes. The 16-light scale is an equal-width discretization of the existing -90..0 native dB-like range, pending physical calibration.
- **Actual native peak latch**. The RX callback records the highest input/output sample received **between approximately 43ms repaint opportunities**. The peak cannot disappear merely because a later native event contained a quiet level before the repaint. This retains actual signal maxima, unlike synthetic TAP-triggered meter peaks.
- **Visual attack and fall**. The M4 processes peak-window maxima at every 100 received DSP frames (~23 updates/second in R05 HW04) using **instant rise**, **2 display ticks (about 86ms) peak hold**, and **12px per display tick release**, roughly 0.30s to decay from an output click at 114px to a ~30px baseline. Each source has separate peak and hold state; two-second existing per-key stale expiry is retained. With missing native peaks the display falls normally: a missing click is not disguised with a fake spike.
- **Read-only Home-paint instrumentation**. The 640-byte editor command `0x13` keeps all 24 native ledger slots exactly at bytes 64..639 and the first 8 diagnostic words at bytes 0..31. The signature advances to ASCII **IOM6**, and the earlier unselected bulk 44-word native floats at bytes 32..63 are replaced with 8 instrumentation words: Home paint callback entries, stock UI redraw requests, packed visual state actually read by Home paint, latest visual state, count of true native high input/output events, pending peak pixels, Home paint callbacks with right LED amplitude ≥88px. This permits discriminating *native missing signal*, *M4 visual envelope*, *redraw requests* and *Home paint callback execution* on physical device. It does **not** measure the final physical LCD transfer/completion and should never be described as such.
- **Exact native IDs preserved**. Left input-candidate `0x00020002/3`, right output-candidate `0x0002002a/1`; the R03C metronome and editor telemetry `0x50`, R01 raw RX capture `0x4f`, 44-word raw diagnostic counter, 24-key min/max/count table, USB Monitor, GR and DSP Usage% original source code are unchanged in binary.

## Reproduction and physical protocol

Rebuild off-device: `tools/build_io_level_r06_segmented_peak_envelope.py`, `tools/plan_io_level_r06_ram.py`, `tools/stage_io_level_r06.py`. A new host read-only decoder `tools/io_level_r06_peak_telemetry.py` reads IOM6 (`0x13`) and the unchanged `0x50` revision check, preserving all 24 native family/parameter ledger rows.

On the Mac mini, after user power-cycles out of the **R05 RAM trial** to the installed **R03C** image, manually open `http://localhost:8765/IO-LEVEL-R06-SEGMENTED-LED-PEAK-ENVELOPE/` in Chrome and initiate the RAM test. Confirm boot success, Home visible with both LED rows, DSP Usage%, original compressor GR, metronome, USB Monitor and guitar path all work. Test separately guitar-only and metronome-only. Assistant can then use the read-only `IOM6` telemetry to compare TAP beats to true native output highs, display envelope highs, actual Home paint callback highs, and UI redraw requests. A still-missing native peak remains a separate upstream issue; no DSP meter code was changed in this experimental image.

**Not a permanent release; no physical R06 evidence yet.** The user controls RAM startup. A normal power-cycle returns to the R03C image.

## Validation and monitoring priorities

1. If startup hangs, record browser error and use a power-cycle to return to R03C.
2. If no LEDs appear but the raw bars react, collect IOM6 0x13 to distinguish native-key receive, display-envelope state, redraw requests and paint callback count.
3. Compare the right native-high event counter, visual state, and actual Home paint high counter across metronome beat windows. Real acoustic or optical display completion still requires separate external measurement.
4. Watch DSP Usage %, GR, USB Monitor, DSP audio and metronome TAP synchronization under both low- and high-DSP presets. The offline worst-case full-LED draw needs 34 rectangle calls vs four for R05; physical CPU/wall-clock benchmarking and any startup freeze are decisive regression checks.
