# METRO-LEDSYNC-R02C-DONOR-EGRESS — exact installed HXtra v1.2.1 LED/audio investigation

## Status

The user reported that the initial R02B2 audible metronome click aligned with the knob-3 TAP LED but drifted after repeated physical BPM-knob adjustments, and that the previously installed per-block DSP usage percentages disappeared. They explicitly require preserving the **exact existing installed HXtra v1.2.1 feature selection**, and synchronization to the **visible LED output**, not to a hidden software beat counter.

**Current state (2026-11-20):** A donor-preserving offline R02C build has passed 16 focused M4/SHARC simulator tests and the L6IA archive verifier, and its RAM-only WebUSB assets have been staged on the Mac mini. **No R02C hardware run has happened yet, and neither physical light latency nor acoustic click latency has been measured.** R02B2 was the last confirmed active RAM image; user initiates any new RAM run. The program has not written permanent device eMMC.

## 1. Source of truth: exact installed donor

The verified installed HXtra v1.2.1 HXF is `/Users/friend/Downloads/HXtra_v1.2.1.hxf`, MD5 `93969635834cd6050dec7f137df1e4b9`, SHA256 `96ac133e094c75f2701226fc7cf3fca4c04b19b91aa34785e646d919979b88c0`. A R02B3-from-stock rebuild omitted USB Monitor and therefore **does not qualify** as an acceptable donor-preserving correction. R02C patches this exact HXF in place at the archive level.

R02C changes only Entry 0 (M4) and Entry 2 (SHARC bootstream). Other 13 of 15 entries (1,3..14) remain byte-for-byte identical to this donor. Entry 0 has exactly five bounded, verified hook sites at `0x28d98f78`, `0x28e045a0`, `0x28d96adc`, `0x28da6138`, and `0x28da6134`; original entry bytes are unchanged outside these sites, ordinary partition metadata/CRC and appended new code. All existing M4 donor hooks and Global Settings data are intact, including donor's original TAP Command and BPM/Tap Color implementations. Entry 3 parameter schemas and model definitions, Entry 4 DSP graph, and every other installed feature are unchanged.

The original installed donor's SHARC `Metronome` kernel at PM `0xe5386` consists of 142 instructions and is **byte-for-byte identical** to `src/sharc/click.asm` in upstream commit `df327d5`, as independently assembled and compared against donor LDR INIT_L48. One and only one original SHARC instruction at `0xe53cf` is replaced with a branch to 15 new instructions at PM `0xe52c4..0xe52d2` in the donor's previously uninitialized PM gap `0xe52c4..0xe52ed`. The 16th padded zero instruction at `0xe52d3` is also in that free PM gap. All other initialized PM words match the donor exactly.

The installed SHARC Entry 2 is `524212` bytes with just 76 bytes of space under its `524288`-byte eMMC partition. The 15-instruction off-line hook requires a new 108-byte LDR section. In the original donor LDR stream, four immediately adjacent tag-4 INIT_L32 descriptors for the exact disjoint contiguous DM ranges `0x200018..0x200037` are combined into one 32-word descriptor at the same position, saving 36 bytes. A full parser independently verifies that all **22,468 initialized DM words have exactly the donor's final values**. Resulting Entry 2 is **524284 bytes**, with **4 bytes of partition headroom**, and only one original PM instruction plus the 16 newly loaded PM words differs. This compression is of equivalent bootstream metadata; no installed DSP functions or model configuration are removed.

`tools/metro_led_donor_patch.py` implements the exact-donor M4 patch with SHA/MD5 gating and byte-level whitelist; `tools/metro_led_sharc_patch.py` verifies exact donor SHARC source and handles the checked Entry 2 transform. `tests/test_metro_r02c_donor_led_egress.py` and `tests/test_metro_r02c_sharc_led_egress.py` simulate the actual encoded M4/SHARC instructions.

## 2. When the visible FS3 TAP ring flashes

The installed firmware's **actual binary** (ARM Thumb disassembly, checked against its sources) establishes this chain:

1. The stock tempo beat task, beginning `0x28d9bdfc`, sleeps 1 ms, obtains a microsecond timebase, checks current period `0x281ccc44` in ms and elapsed half-beat time, then toggles its phase when more than half the period has elapsed. The period is derived from `60000 / BPM`. The task reaches its **logical beat ON** callback at `0x28d9be92`, which calls the donor's Tap Command `tc_on` at `0x28e55060`. It then calls the LED driver's `LED_MODE(2,1)` (`0x28db8260`) to light FS3 or `LED_MODE(2,0)` to turn it off. These are separate operations from the software logical beat.
2. `LED_MODE` updates a per-footswitch mode byte (`0x281f35f8 + LED index`) and driver state. In mode 1 it obtains the ring color and calls `0x28d98f74` with the LED index and RGB. In mode 0 it obtains a literal zero from `0x28e39cc0` and calls the same sender. The actual donor byte value at `0x28e39cc0` was verified to equal zero.
3. Crucially, the tempo period setter `0x28d9bef8`, used during a BPM setting change, assigns FS3 **mode 2** (autonomous driver blink), updates the half-period in `0x28db8138`, and the LED task at `0x28db7f04` can send its own lit/dark transitions through the same LED sender. These transient LED illumination requests need not correspond one-for-one to `0x28d9be92` events during BPM adjustment; therefore an internal beat counter is **an unreliable direct proxy for the visible LED**.
4. The donor's `HX_BPM` feature intercepts `0x28d98f74` at `0x28e4d632` (`bpm_ledsend`), notes each ring's color and visibility, and masks outgoing TAP colors to black when TAP Tempo LED is configured off (`bpm_data+6`, confirmed at `0x28e4daee` by donor disassembly). It then tails into the original sender's continuation `0x28d98f78`. The original sender passes processed RGB to the hardware LED controller path (`0x28d9d72c`). Thus **`0x28d98f78`, after filtering**, is the most useful low-level firmware reference for the physical FS3 OFF→ON request, covering both ordinary beat-task illumination and mode-2 autonomous blinking.

R02C M4 hook intercepts precisely `0x28d98f78`, reproduces the four displaced donor Thumb bytes, forwards all original register values and sender behavior, and counts only FS3 (index 2) processed RGB changing from zero to nonzero when FS3's installed function byte `0x28128a78` is TAP (1). Changes of the ring color *while already lit* do not count as new flashes; repeated RGB commands are deduplicated. Re-engaging slot 8 Metronome sets a pending bar reset; the **first subsequent actual FS3 illumination request** (never the re-engage operation itself) toggles one high-bit reset marker and starts the accented downbeat. Bypassed ticks are not published.

When FS3's role is Preset/Snapshot/other, the M4 transport invalidates the external timing marker so the SHARC retains the exact original donor local metronome. When the donor's actual `bpm_data[6]` shows TAP LED invisible, it similarly invalidates the marker, ensuring setting Tap LED Off does not silence the metronome. Checks use direct reads and bounded integer logic, with no locking application functions, no VFP and no changes to donor's LED sender itself.

**Observed on R02B2 hardware before this patch:** a nine-second read-only M4 driver-mode trace of the current FS3 TAP LED produced 11 sampled LED driver mode ON transitions and 11 internal TAP-count changes. The ~130 ms sampling/reply intervals caused apparent offsets of up to 133 ms; these are *host sampling artifacts*, so they cannot measure real LED/audio delay. The trace confirms normal LED state and count correspond in steady state but does not validate BPM-changing behavior. No photodiode or synchronized light/audio recording has yet been made.

## 3. Audio phase behavior, test scope and unresolved measurement

The original SHARC metronome uses its `Time`-to-sample interval for independent timing. R02C taps the actual validated M4 SPI TX buffer at SHARC DMA words `0xc3da6..0xc3da9` (the address mapped during R02B1E hardware analysis), in which M4 publishes its **post-filter FS3 LED-on count**, enable counter, marker and XOR checksum. With a valid external marker, unchanged count suppresses locally scheduled beats; a changed LED count makes the original `c_tick` run at the first sample of the next 16-sample audio block. A high-bit counter transition from the M4 pending re-engage resets the bar to accented downbeat before `c_tick`. With no valid external marker, the donor's original independent metronome timing remains. The user's test is specifically preset **41C, Time 1/4, Accent 4, FS3 TAP visibly flashing**. Other subdivisions, different footswitch LED choices, and exact acoustic-to-optical offset require separate tests.

**Important measurement distinction:** a post-filter M4 command is the firmware's actual requested illumination edge. The user's eye sees light after the LED panel-controller serial transmission and electronics respond. The SHARC audio path has M4→DSP SPI framing and 16-sample blocks (48kHz ⇒ 0.333ms), as well as audio output buffering. We have not yet measured either end-to-end latency, so do not claim sample-accurate synchronization to photons. This firmware design uses the most downstream identifiable LED event without altering the installed LED driver.
