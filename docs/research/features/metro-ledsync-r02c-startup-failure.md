# METRO-LEDSYNC-R02C-HWFAIL01 — frozen application startup, November 20, 2026

## Observed outcome

The user reported R02C froze on startup immediately following its first attempted RAM-only hardware load: **"freezed on startup"**. On the Mac mini, a read-only USB probe detected `HX Stomp` enumerated as a Line 6 USB device; invoking `.venv/bin/python tools/hx_ctl.py --timeout 2 status` returned `error: no SYN reply from the device within 2.0 s`. The browser's local HTTP server log shows it served R02C's nine RAM transfer regions. The original browser transport-execution log has now been recovered and appended below: nine CRC checks passed and the loader reported successful RAM execution transfer; the exact frozen screen and availability of audio passthrough remain unverified. USB enumeration alone does not conclusively locate the fault inside the M4, but the failed editor handshake and user-observed freeze establish a **hardware startup failure**.

**Do not run R02C again as a normal test candidate.** Its WebUSB runner (`web/experiments/metro-ledsync-r02c/index.html`) is disabled with an explicit failure notice. Since the failed firmware is RAM-only, a physical power cycle should restore the user's original installed HXtra v1.2.1; successful restoration after the user's most recent attempt has not yet been separately observed. This failure supersedes the positive offline claims of tag `metro-ledsync-r02c-donor-egress-20261120`.

## Source and forensic observations since report

- Original R02C artifacts were built from the exact donor HXF SHA256 `96ac133e094c75f2701226fc7cf3fca4c04b19b91aa34785e646d919979b88c0`, MD5 `93969635834cd6050dec7f137df1e4b9`. R02C staged HXF SHA256 `c718cdb42429cc2b68411d80ede50fb341d8588db3e92bd35cf5c0c180d57126`; its 13 other L6IA entries were byte-identical to donor, Entry0 five whitelisted M4 hook sites and appended module, Entry2 SHARC click trampoline and bootstream changes. The L6IA archive checksums were previously verified; checksums and simulations did not detect startup incompatibility.
- The original M4 LED sender and the modified R02C M4 LED sender were executed *in actual extracted code* under Unicorn via `tests/test_metro_r02c_led_fullpath_startup.py`. For FS3 TAP, visible and dark LED colors, another footswitch assignment, and TAP LED Off, both returned to the same stop address, restored the same stack pointer, and reached the original downstream LED hardware send routine. This excludes one simple stack/trampoline mismatch **for those simulated contexts**; real startup ordering, interrupts, mutex ownership, hardware memory effects, and the SHARC bootstrap are not reproduced.
- `src/m4/gr_meter.s` independently supports that GR's receive callback accepts the SPI RX frame in r1. The donor RX callback already points to GR's code and the R02C event probe's register assumption agrees with this source. Other possible effects remain untested.
- The SHARC LDR bootstream is almost full: R02C entry2 length `524284` of `524288` available bytes. Its exact installed kernel had 142 instructions and one was replaced with a branch into a previously unused 15-instruction SHARC PM shim. Four short contiguous data-load records were merged into an equivalent 32-word record, saving 36 bytes. Complete final initialized DM values are identical offline, but hardware bootloader's record ordering, prefetch/partition boundary effects, and DMA execution remain **unverified**. This near-boundary representation is a plausible startup failure mechanism, not an established cause.
- The generic RAM loader modifies a small M4 eMMC read/write hook on boot even when the source firmware image is unchanged. We had **not** previously run this exact installed HXtra v1.2.1 donor HXF as an unchanged source through the same RAM loader. R02B2's startup success used a different rebuilt firmware composition and thus does not settle that baseline compatibility.

## Control execution misidentification (HWFAIL01 follow-up, 2026-11-20)

After rebooting out of R02C's startup freeze, the user said the unchanged-v1.2.1 control had been loaded and reported that DSP percentages were missing. The initial USB `status` query succeeded on preset 41C, and I mistakenly **reported that as proof the unchanged-donor RAM control had booted**. That inference was false: `status` verifies the editor and selected preset, **not the firmware image identity**.

A subsequent live, read-only USB diagnostic command `0x50` returned revision `METRO-TAPSYNC-R02B2-AUDIO-PHASE` with its exact R02B2 revision sentinel, dynamically advancing M4 TAP and SHARC echo counters and valid echoed checksum. Source evidence: `tests/hardware_evidence/METRO-DONOR-V121-CONTROL-MISLOAD-R02B2-20261120.jsonl`. The live Globals menu had only seven categories (last `BPM Display`) and the DSP percentages were missing, precisely matching the R02B2 HXF's `CAT_MAX=6` and omission of `HX_DSP_METER`. On the user's explicitly identified installed reference `~/Downloads/HXtra_v1.2.1.hxf`, the Entry0 M4 image instead has `CAT_MAX=8` (nine categories), `DSP Usage Display` and `Breathing Line` categories, and DSP-meter edit/browser-paint hooks; the R02B2 HXF has no `DSP Usage Display` string, stock browser paint position and name spacing. The absent DSP percentages are thus explained by **the active R02B2 firmware**, without requiring a change in the user's original Global Settings.

Chrome inspection found only the R02B2 test tab, with a full successful WebUSB RAM-run log (nine region CRC checks, successful RAM execution transfer). The R02B2 browser tab has now been navigated directly to `http://localhost:8765/METRO-DONOR-V121-UNCHANGED-RAM-CONTROL/`, whose DOM explicitly reports `stage: Ready`, `runDisabled: false`, nine RAM regions, one reference eMMC check and RAM-only writes. No Global Settings value was changed while navigating to inspect the missing percentages; the display was returned to the original 41C Metronome edit screen. The current live pedal still reports the R02B2 signature.

**Correction of investigation status:** The unchanged HXtra v1.2.1 application positive control **has NOT been executed successfully on hardware**. The preceding claims of a successful unchanged-donor control boot are withdrawn. That control must be user-initiated from the correct browser page, followed immediately by a build identity check using the actual LCD category structure and/or a verified image-specific hardware diagnostic. A successful USB `status` alone is an insufficient acceptance criterion. The R02C failure's root cause remains unisolated between the RAM boot environment and its code changes. Offline M4-only and SHARC-only ablations remain untested.

## HWFAIL02 SHARC-only physical freeze and metadata forensic correction

The user explicitly reported the isolated `METRO-LEDSYNC-R02C-HWFAIL02-SHARC-ONLY` image also **froze during startup**. The original M4 application and other 13 firmware entries were byte-identical to the installed HXtra 1.2.1 donor, so **SHARC Entry2 changes alone** can cause this failure. On the Mac mini, USB enumeration survived but the editor SYN handshake timed out after two seconds. Original Chrome WebUSB log saved as `tests/hardware_evidence/METRO-LEDSYNC-R02C-HWFAIL02-SHARC-ONLY-20261120.json` (SHA256 `883b11bc7596d3fe0f4b17cbcb521aef9def480e440da0575c2dfdeebc5f097e`): nine SDRAM CRCs all passed and the RAM execution handoff was reported, but physical eMMC CRC remained unavailable (`0x10b`). The failed HWFAIL02 browser page is disabled and staged to the Mac mini.

**Important newly discovered planner bug:** `hxf_ram.overlay()` substituted modified Entry2 **payload** sectors but left the original installed subheader sector `0x8802` untouched. That subheader still advertised a 524,212-byte SHARC LDR stream and original CRC `0xc273d05e`, although HWFAIL02 installed an HXF with a 524,284-byte payload and CRC `0x0f5d02e7`: an exact **72-byte length inconsistency**. The original donor boots and the earlier working R02B2 image was shorter than the donor, whereas the two failing SHARC images were longer. This is a verified, material inconsistency; whether the device reads this length in the path responsible for the freeze remains a hypothesis.

A single-factor corrective RAM overlay `METRO-LEDSYNC-HWFAIL03-SHARC-HEADER-ONLY` reuses **exactly the same SHA256-pinned failed SHARC-only HXF** and the original donor M4. It adds only one corrected metadata header sector `0x8802` to the previous 11 payload overlays. New plan SHA256 `a2e8544700df9032ec5aceab6b802f4e563fafe4a13e401653a9aae3b5cfc233`, 12 overlay sectors, nine RAM regions, no eMMC writes. Offline validation reconstructed every sector of the candidate SHARC partition and compared all original overlay bytes to HWFAIL02. The user-initiated Chrome page is on the Mac mini at `http://localhost:8765/METRO-LEDSYNC-HWFAIL03-SHARC-HEADER-ONLY/` and preflight showed **Ready**. Hardware outcome is **pending**. A separate size-preserving R02D image (Entry2 exactly 524,212 bytes) also passed offline tests but remains **offline**, to avoid confounding the HWFAIL03 one-factor experiment.

For detailed evidence, tables, hashes, and the controlled comparison, see `docs/research/features/metro-ledsync-hwfail02-header-overlay-diagnosis.md`.
