- M4 post-filter FS3 TAP accepted LED event counter **332→337**, bit31 true.
- SPI TX frames stamped **401065→406290**, increase **5225** over ~2.26s between first and last observations (~2314/s).
- Last M4 TX event and bitwise complement correct at every observed snapshot; last sent count matched current M4 event count.
- M4 cumulative skipped SPI frames **16204**, noTAP/LED-hidden frames **3832**, short OFF→ON reversals filtered **3**, and bypass handler engage transitions **0**, all **unchanged during this read-only sampling interval**.

Non-increasing cumulative noTAP/skipped counters during this short sample cannot rule out earlier intermittent conditions. The M4 initial `mp_active=1` despite editor showing Metronome bypassed merits a separate bypass/engage state audit and must not be silently treated as a validated state.

## Two independently reproduced R03B defects (software facts)

1. **Out-of-order but correctly complemented SPI pairs trigger phantom clicks.** R03B's SHARC receiver validated that the counter and bitwise complement matched but then tested only `R8 XOR C_LED_LAST !=0`. It accepted a *complete old packet* that arrived after a newer packet. Actual assembled SHARC simulation for a steady master with counter values `0x80000001 → 0x80000002 → 0x80000001` incremented the beat count **2→3** on the stale packet. Restoring `0x80000002` could trigger another click. Full pair integrity does **not** enforce event recency. Failing negative regression: `tests/test_metro_led_r03b_hwglitch_regressions.py::test_older_consistent_spi_frame_must_not_create_ghost_click`. The test is now marked `xfail(strict=True)` for R03B, and its R03C counterpart passes.
2. **Transient invalid TAP mode packets can release the independent native click clock.** R03B M4 published `(0,0)` immediately if any TX callback found FS3 TAP/LED visibility temporarily false. The R03B SHARC treated that as donor native Time mode. Simulating a genuine physical LED event followed by 0.1s of these frames generated a **local click with no fresh LED edge**, and the subsequent genuine LED event could generate another. Reproduced against actual SHARC assembly in `tests/test_metro_led_r03b_hwglitch_regressions.py::test_interrupted_master_must_not_add_local_click_then_led_click`, also marked strict expected failure for the known old version. **The physical cause of the user's own clicks remains unproven**: the M4 counters do not show receiver reordering, local SHARC mode transitions or acoustic timestamps.

Both are demonstrable design defects and merit repair irrespective of which produced this particular report.

## R03C implemented changes

**In-place SHARC forward-only event receiver:** From the pinned R03B source, retain full word240/241 bitwise complement validation. For a coherent event, calculate the 32-bit difference `R8 - C_LED_LAST` and shift left one bit to remove the independent epoch bit31. Then use a signed positive test on the resulting doubled low31 difference. Only strictly forward count changes trigger audio, update `C_LED_LAST`, or allow a new epoch downbeat. Exact prior/duplicate counter, backward replay, or an old epoch after a new one remain silent. The proof relies on practical forward jumps having a low31 delta in the range 1..2^30−1; the 31-bit wraparound would require more than 2 billion beats and is outside the experiment's realistic horizon. This is **not** a general-purpose replay-protected authentication protocol or a guarantee against correlated two-word corruption.

**Maintained original metronome kernel shape:** Factor the original gain polynomial by `2^-17` and increase the `SCALB` exponent by 17, saving two instructions. Because this is an exact power-of-two float exponent shift away from underflow/subnormals, 11 parametric donor waveform comparisons at the original 16-sample block rate remain **bit-for-bit identical**; additional ssim checks explicitly covered time/level extremes and the user's observed level value. The new ordered receiver and 6ms envelope remain within the donor's original **142 PM instructions**, at `0xe5386`, with the original 201 LDR records and **524212-byte** Entry2 size. Only program data in existing record #177 differs; all descriptor tags, lengths, base addresses and record ordering are unchanged. The final NOP after RTS is unreachable padding.

**Transient native clock release debounce on M4:** Initial non-TAP mode preserves native donor Time immediately. Once actual TAP mode is active, M4 holds the most recent valid event/complement pair through up to **4600 consecutive non-TAP SPI frames**, approximately 2 seconds at the live measured ~2300 frames/second. This prevents a momentary mode/visibility change from activating a parallel native oscillator. If non-TAP persists past the threshold, M4 publishes `(0,0)`, returning to original donor mode. When actual TAP resumes, the streak resets to zero and the receiver reacquires genuine forward LED events. This **frame-count hysteresis** is an explicit assumption, not a guaranteed wall-clock 2 seconds for every device load; if transport frame rate changes significantly it can deviate. The user can still switch FS3 mode intentionally but native Time-mode reappearance may have a finite delay after leaving TAP. The 20ms short-dark-interval filter is unchanged from R03B, based on the six short reversals in the earlier R01 physical knob trace.

**Read-only M4 timing probe (new):** The M4 remembers the actual native microsecond timestamp of each accepted final post-visibility-filter FS3 LED ON command, and on its first subsequent SPI TX event stamp measures the difference using the **same original M4 microsecond clock**. The 84-byte USB editor command `0x50` reports latest accepted M4 LED timestamp, latest TX event count, **LED-command-to-first-M4-TX latency in microseconds**, TAP loss grace/fallback counters, M4 active/bypass flags, and last checksum. Producer uses the previously successful original M4 timer and hooks; timer alignment and exact delay were verified in the Unicorn simulator, e.g. simulated 700us and 355us elapsed yielding exactly those numbers. **It does not measure downstream SHARC receive latency, codec/audio output latency or optical LED hardware**. The user's perceived lag therefore remains **unfixed and unquantified**. Any later compensation or predictive audio timing must be based on actual hardware audio vs optical timing and cannot be justified by the M4 TX time alone.
