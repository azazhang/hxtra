# METRO-TAPSYNC-R02B3-BPM-RELOCK-DSPMETER

**Scope:** HX Stomp 3.80 + installed HXtra v1.2.1 RAM-only experimental metronome synchronization. Fix a physical-BPM-knob drift regression in R02B2 and restore donor UI/features omitted by the earlier rebuild. This document is the source/QA ledger; it is distinct from `metro-tapsync-r02b2-audio-phase.md` and its `HWQA01` test results.

**Current disposition:** corrected source compiles, new regression tests and exact donor M4/UI audits pass, RAM image/plan independently verified on Mac mini. **Audio phase on physical pedal with repeated physical BPM-knob changes has not yet been retested in R02B3.** The actual pedal remains on the prior R02B2 RAM image until a user-initiated R02B3 WebUSB run.

## 1. Confirmed timing defect and correction

User's observation on R02B2: initially the click sounded synchronized with the physical TAP/knob-3 LED. After several BPM changes using the panel knob, phase drifted perceptibly.

The actual compiled R02B2 SHARC metronome kernel was reproduced with `ssim`. With a 500 ms original beat, 350 ms elapsed since the last real M4 TAP edge, and an abrupt new 100 ms Time value but **no new TAP edge**, R02B2's local fallback tested elapsed 350ms against `2 * NEW_TIME = 200ms`, switched `C_SPI_MASTER` from 1 to 0 and generated a **phantom click**. Beat-in-bar advanced 1→2 without an M4 TAP event. The next actual TAP restored the master but the accent counter was displaced. Further, a single corrupt SPI frame bypassed the external-sync guard and could produce the same false local beat on a tempo edit; after a genuine dropout, relocking retained arbitrary local accent phase.

R02B3 updates `src/sharc/click_spi_phase.asm`:

- Keep `C_SPI_HOLD_PERIOD` in the SHARC metronome instance at offset 33, the nominal Time in samples measured at the **last real M4 TAP**. At every callback, external dropout threshold is `2 * max(held_period, current_period)`, so turning BPM faster does not retroactively time out an old tempo interval. Refresh held period on the next real TAP, initial stream acquisition, and metronome re-engage.
- When an isolated frame has invalid marker or complemented-XOR checksum after a valid TAP stream was acquired, leave that frame out of the event chain and retain the last real TAP master. Prior R02B2's invalid-frame path could jump immediately to the local oscillator and create false ticks.
- After a genuine extended TAP dropout enters local fallback, the first returning TAP resets the bar/oscillator and creates an accented downbeat on that exact event; subsequent TAP events advance the bar. No off-grid local accent is carried across a relock.
- The pre-existing enable behavior is preserved: M4's grid position 8 bypass→enabled hook increments an integer counter. The SHARC receives the new enable value, clears the oscillator/envelope and bar state, discards TAPs while bypassed, and waits until the **next** M4 LED-ON/TAP edge to play the accented downbeat. There is no immediate offbeat re-enable click.
- Scope remains preset 41C's quarter-note Time=1/4 with Accent=4. Other subdivisions require separate handling; actual LED/audio offset has not yet been measured.

**Regression tests:** `tests/test_metro_r02b3_bpm_relock.py` first **failed 3/3 against R02B2**: (1) tempo acceleration triggers false beat, (2) corrupt SPI during tempo edit triggers false beat, (3) first real TAP after dropout keeps wrong accent. After implementing the correction, all five tests pass, including six successive fast/slow BPM changes without a TAP event and a test that the stored last-real-edge tempo updates only on an actual TAP. Ten inherited R02B2 click/oscillator tests continue to pass after updating the expected relock accent behavior. Binary Thumb M4 SPI event bridge remains bounded and uses no settings locks or VFP.

## 2. Donor firmware parity audit and restored UI

Prior builds had reported **792/792 model schemas identical to installed HXtra 1.2.1**, but that check was limited to Entry 3's models/parameters. It failed to assess M4 UI features and the separate browser-title table. The exact installed HXF at `~/Downloads/HXtra_v1.2.1.hxf` is the authoritative reference.

Independent Entry0 M4 hook-site comparisons against stock HX Stomp 3.80 and the installed HXtra v1.2.1 donor identify the following donor features omitted by R02B2 and rebuilt in R02B3: `HX_LABEL_COLOR`, `HX_TUNER`, `HX_TAP_COLOR`, `HX_BREATHING_LINE`, `HX_DSP_METER`, `HX_LONG_PRESS`, `HX_PRESET_COLOR`, `HX_MORE_SNAPSHOTS`, and `HX_REAL_NAMES`. The donor also has `HX_CC_TAP`, now restored; `HX_BPM` was already present. `HX_GR`, `HX_CLICK`, `HX_FX_GATE`, `HX_GATE_SC`, one NAM slot, `HX_USB_INPUT`, and the diagnostic `HX_SCREEN_MIRROR` remain enabled. The latter two are test conveniences, and were not necessarily installed in stock HXtra.

- **DSP percentages:** `HX_DSP_METER=1` again patches the Edit-view and Browser paint handlers. The omission in R02B2 is the verified cause of the missing per-block percentages, independent of the beat timing change. The donor had `DSP Usage Display` and the virtual `Browser`, `Blocks`, `Total` settings; the repaired image restores them.
- **Expanded model names:** Entry0 Table 2 of the donor has 827 browser entries. For 492 entries, the title differs from stock Line6 3.80; R02B2 reverted all 492 to stock, while the R02B3 image's entire Table 2 title mapping matches the donor **827/827**. No change in 792 DSP model definitions or parameter layouts.
- **Tap Command coexistence:** the donor's `HX_CC_TAP` also owns the `0x28d9be92` M4 beat-on callback, which R02B2 previously took over alone. Under `HX_METRO_SPI_PHASE=1`, `tap_command.py` defers only the shared `tc_on` site. `metronome_phase.py` runs later (`ORDER=121`), links the original `tc_on` in `METRO_PREV_BEAT`, then its M4 event hook calls `tc_on` and increments its own counter once. Other Tap Command functions are untouched. A Unicorn test executes the actual new Thumb hook against a test stub `tc_on`, confirming original return and exactly-one delegation.

**Known parity exception — USB Monitor:** HXtra's installed donor has `HX_USB_MONITOR=1`, allowing Path A routing options (Main L/R, Send/USB, USB Only, Main+Snd). The attempted full R02B3 build with USB Monitor plus the revised audio/GR/other code failed the explicit `Entry 2 size <=524288` partition check: **524852 bytes**, excess **564 bytes**. R02B3 excludes `HX_USB_MONITOR` to retain the installed one-NAM-slot model schemas, the metronome sync fix and other donor UI features. Its routing options are absent in the temporary RAM image; the permanently installed v1.2.1 still has them. The code must be optimized within the 512 KiB SHARC partition before they can be combined. **Do not describe this image as full feature parity.**

**Reproducible build script:** `tools/build_metro_r02b3.sh` pins every feature flag, source HXF and output identity, explicitly unsets USB Monitor, and skips only the previously validated NAM simulator rebuild with `--no-check`; archive checks and the RAM planner still run. Donor-specific tests `tests/test_metro_r02b3_donor_parity.py` independently compare the donor/stock/repaired images, not source comments.

## 5. Offline test and build disposition (2026-11-20)

- **Actual full suite:** `pytest` ran the R02B3 M4 Thumb/SHARC binary tests, old R02A bridge, dynamic event echo, GR compressor, click/metronome, NAM/HXtra model and preset, DSP meter, BPM, tuner, TAP LED color, breathing line, long press, snapshots, preset color, USB Monitor standalone, Tap Command, real model names, label color, and RAM loader tests. It returned **1,187 passed, 1 failed, 1 deselected** in 309.62 seconds. The one deselection `tests/test_ramrun.py::test_built_files_match_source` is the known absent local ARM `nano.specs`/newlib; the actual RAM loader is the unchanged working upstream byte stream.
- **Failure root cause:** `tests/test_tap_command.py::test_build_sends_every_site_to_the_module` called `firmware.built({'HX_CC_TAP':'1'})` with global `HX_METRO_SPI_PHASE=1` still present. It expected Tap Command to own `0x28d9be92`; our R02B3 correct **combined** build deliberately lets Metronome's wrapper own the call and invoke `tap_command.tc_on` as its predecessor. That one test was wrongly treating a combined build as an isolated Tap Command build. The original independent coexistence test `tests/test_metro_r02b3_tap_command_chain.py` already passed and verifies the chained behavior.
- **Test-only repair:** `test_build_sends_every_site_to_the_module` now explicitly uses `monkeypatch.delenv('HX_METRO_SPI_PHASE', raising=False)` to test *isolated* `HX_CC_TAP=1`. Immediately reran that previously failing exact test, the real M4 combined hook test, all six donor-parity comparisons, and five BPM drift/relock tests with the same stock HXF and R02B3 flag. **12 passed in 6.93 seconds**. These cover the sole full-suite failure; no firmware implementation was altered in this repair. Every distinct test that ran in the expanded suite is now confirmed passing, but a single repeated full 1,188-case run after the test change was not performed.
- **Image compatibility audit:** 792/792 complete DSP model/parameter layouts and 827/827 browser names match the donor exactly; 492 names restored from the installed HXtra 1.2.1. Unit test compares installed/stock/R02B3 M4 hook sites and unique settings strings including the per-block DSP meter. R02B3 branch's M4 Tap Command event callback delegates to the donor's `tc_on` and emits one M4 beat counter increment; Unicorn verified.
- **Physical behavior pending:** The new image has **not** been loaded on the pedal, and the user's reported physical-BPM-knob-induced click drift has not been re-measured acoustically. It is ready for an identified RAM hardware run; do not mark the audio defect fixed on hardware merely because the SHARC regression passes.
