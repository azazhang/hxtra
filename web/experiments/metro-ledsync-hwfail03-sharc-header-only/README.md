# METRO-LEDSYNC-HWFAIL03-SHARC-HEADER-ONLY

A one-variable follow-up to the confirmed HWFAIL02 SHARC-only startup freeze. The original **SHARC program HXF is byte-identical** to failed HWFAIL02 (SHA256 `3aa8d41b6d925272a00db2a16f2c112d1399f0adde70131ee3f78d47c09cf2ce`). It includes the original installed v1.2.1 M4 and every other non-SHARC entry byte-for-byte, with DSP Usage Display and USB Monitor unchanged. The only difference is that the RAM overlay includes one additional, corrected eMMC subheader sector at `0x8802` with Entry2 CRC `0x0f5d02e7` and payload length 524,284 bytes.

Run `PYTHONPATH=tools python3 tools/metro_led_hwfail03_header_only_plan.py "$HOME/Downloads/HXtra_v1.2.1.hxf" build/startup-isolation/METRO-LEDSYNC-R02C-HWFAIL01-SHARC-ONLY/METRO-LEDSYNC-R02C-HWFAIL01-SHARC-ONLY.hxf build/browser-ramrun/METRO-LEDSYNC-HWFAIL03-SHARC-HEADER-ONLY/regions` to reproduce the new plan. Plan SHA256 `a2e8544700df9032ec5aceab6b802f4e563fafe4a13e401653a9aae3b5cfc233`, 9 RAM regions, 12 overlay sectors, 3 runs, 1 donor CRC check; no permanent eMMC writes. This versioned browser page is served on the Mac mini at `http://localhost:8765/METRO-LEDSYNC-HWFAIL03-SHARC-HEADER-ONLY/` alongside the generated `regions` files and the existing unchanged upstream RAM loader `firmware-ramboot.dfu`. The loader never installs the HXF to the pedal.

The exact cause of the old startup freeze is provisional: adding a physical RAM metadata sector fixes the demonstrated stale length/CRC mapping, but **HWFAIL03 has not run on the real pedal**. The user must power-cycle out of HWFAIL02 before choosing the pedal in Chrome. The next observation is simply whether the original UI and USB editor respond normally. Do not change metronome parameters, presets, or global settings for this test. Power-cycle if frozen. Preserve the browser log as actual hardware evidence.

A second candidate `METRO-LEDSYNC-R02D-SHARC-SIZE-PRESERVED` is offline only; its different compact LDR content is *not part of this one-variable test*.
